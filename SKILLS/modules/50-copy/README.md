## 为什么不再用 `ranking-rules.md`

旧 README 写着「规则草稿在 `vendor/amazon-listing-builder/reference/ranking-rules.md`，等前面模块稳定后搬过来」。核查后发现三件事：

1. **它不在上游仓库里**。上游 `amazon-listing-builder/reference/` 只有 5 个文件，本地有 6 个，多出来的就是 `ranking-rules.md`，时间戳比其余 5 个晚一天（11-13 10:11），是本项目自己写进 `vendor/` 的草稿。
2. **它引用的东西不存在**。文件里写 `keyword-research v2.0 的 handoff.md`、`T1 取 R≥0.9 / T2 取 R 0.6-0.9`，但 `T1/T2` 全文从未定义，`handoff.md` 在上游和本地都查无此文件。
3. **它自己内部矛盾 13 处**。标题 5 槽 vs 4 槽、每点埋 2-3 词 vs 至少 3 词、五点「不是给算法看的」vs「每点埋 2-3 个 P1 词」。

所以：**该文件全部条款作废，本模块不采用。** 这是它留在 `vendor/` 里违反「改 modules 不改 vendor」的连带结论。

## 主规则从哪来

全部指向上游真实存在的文件，逐行可查：

| 规则 | 上游文件:行 |
|---|---|
| 5 层词库 → 6 个字段 | `workflow/step-1-keyword-library.md:63-71` |
| 字段字符/字节边界 | `prompts/compliance-check-prompt.md:77-84` |
| 红线词表 | `prompts/compliance-check-prompt.md:138-152` |
| 空话 → 具体 | `reference/common-mistakes.md:79-85` |
| ST 五条 | `prompts/master-prompt.md:100-104` |
| P0/P1 覆盖检查 | `prompts/master-prompt.md:122-126` |

补丁只有 3 条（上游确实没有的）：P0 未覆盖 = FAIL、五点冒号+分号+句末无标点、描述零 HTML。后两条来自亚马逊官方页面，不是上游。

## 为什么埋词不设配额

上游 `ranking-rules.md` 草稿写「每点埋 2-3 个 P1 词」，`step-5` 写「至少 3 个」。实测本项目 22 条卖点里**只有 4 条有 ≥3 个支撑词**，用户选定的 5 条里有 2 条支撑词为 0。硬闸门会让每条 listing 永久 FAIL，闸门就失去意义。

用户 2026-11-16 提供的埋词 SOP 里那句 `Keyword coverage is an optimization objective, not the ultimate measure of copy quality` 给了另一条路：**改成优先级制**。于是：

- L0 事实层（事实准确 > 搜索量）→ 违反即 FAIL
- L1 表达层（自然优先、不为覆盖牺牲清晰）→ 违反即删词
- L2 覆盖层（整短语优先、跨字段不重复）→ 违反即 WARN

覆盖面从「数词够不够」退到「查有没有违规」，`check_copy.py` 的主力职能随之改变。

## 两个分数体系不混

- **不造评分**。评分走 `amazon-listing-doctor` 的 CDQ 权重（官方口径，六维加权）。
- **本模块只出三态**：PASS / FAIL / WARN。
- **覆盖率不进分**。它只在 `CP-03-覆盖清单.csv` 里报数。

理由：自己拍一套 0.25/0.20/0.15 权重，等于造第二个真源，而 `_common/输出规范.md` 第一条红线就是「混口径相加」。

## 踩过的坑

1. **`root` 列不是词根**。词库的 `root` 存的是语义维度（共性/品类/属性），不是英文词根。第一版 C5 拿它当词根，结果检查永远通过——静默空跑比误报更危险。现在从 P0/P1 关键词的 token 现推。
2. **描述密度不能用短样本**。16 词的描述里命中 4 个词，按 100 词折算成 25/100，会误判。已加 `desc_density_min_words: 100` 门槛。
3. **名词串联要按标点切**。`Kitchen Sink, Sink Caddy` 跨逗号被连成 4 个名词，误报。现在按 `,;:.!?()[]|/` 切段后检测。
4. **C0 缺输入时不许落盘**。第一版会把三个空产物写进一个不存在的品类目录，`调研/__none__/copy/` 就是这么建出来的。
5. **词表两处维护必然漂移**。禁用词表真源只在 `copy_config.yaml`，`references/04-禁用表.md` 只解释不重复列词。

## 2026-11-17 修订：把规则从"卡项目"改成"推项目"

首次用真实文案跑全 12 项检查，暴露三处口径问题，全部只改配置与判定，不动文案标准：

| 问题 | 实测 | 改法 |
|---|---|---|
| C5 词根一刀切 ≤3 次 | `sink` 7 次、`holder` 6 次必然超限 | P0 品类核心词根放宽到 8 次/五点 4 条；P1 保持 3/2 |
| C11 描述密度 ≤3/100词 | 实测 21.0，差 7 倍 | 改为只报数。口径本身就错——`target` 收的 P0/P1 token 就是描述里的普通名词 |
| C6 描述用 20 词上限 | 描述天然比五点长 | 描述单独给 30 词 |

同时把事实卡必填拆成 `required_hard`（14 项，缺了 FAIL）与 `required_soft`（5 项，缺了只提示）。
**事实卡是推动项目的工具，不是卡项目的闸门**——拿不到的事实，文案绕开就行，不该让整篇写不成。

改完实测：`FAIL 0 / WARN 5 / PASS 9`，剩下 5 个 WARN 全是真问题（P1 词根堆词、名词串联、亮点重复标题、P1 未覆盖无归因、五点偏短）。

## 2026-11-17 新增：第三方体检评分（`04_评分`）

规则层只回答"有没有违规"，不回答"内容质量值几分"。补这一块用的是外部项目，不自己造分。

**来源**：[amazon-listing-doctor](https://github.com/buluslan/amazon-listing-doctor) v0.4.12，MIT，原样放在 `skills/vendor/amazon-listing-doctor/`，**未改一行代码**。版本、提交号、口径差异见该目录 `SOURCE.md`；`skills/README.md` 的「致谢」表有完整署名。

**接入方式**：只搬格式。`skills/scripts/score_copy.py` 把 `copy.json` 归一化成它的输入格式（`CP-07a-评分输入.json`），调它的 `compliance_report.py`，把输出摊平成 `CP-07-评分明细.csv`。工具缺失时 `04_评分` 写真「未执行」并继续，不拦主流程——**第三方工具不该成为交付的单点故障**。

**为什么放在第 4 张表**：它和原来的问题清单回答同一个问题「现在还有什么要改」，只是换成打分视角并带外部依据。原 `04_问题清单` 顺移到 `05`（内容不删，它是 08 自检的定位表），`06_自检` 保持最后。

| 问题 | 数据 | 处理 |

| 后台 ST 与五点重复词 `rv` | 合规失败项 1 条；backend 卫生度 0.75 | 删 `rv` → **A9 87→94、失败项 1→0** |

| COSMO / Alexa 建议补 `travel` `gym` `waterproof` | 两维分数 45 / 0 | 不采纳。前两个是通用本体未收敛；`waterproof` 是本品红线（无实测） |
