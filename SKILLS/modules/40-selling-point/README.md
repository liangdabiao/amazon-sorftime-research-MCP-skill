# 40 · 卖点提炼（输出型模块）

产出**卖点库**：一行一个卖点，带证据链、权重、角色、等级，可直接交给 `50-copy` 排五点。

2026-11-16 用 sponge-holder（30 ASIN / 164 条五点 / 309 条评论）跑通，22 个卖点 / 427 条证据 / 7 项自检全过。
产物在 `调研/sponge-holder/selling-point/`。

## 输入

| 来源 | 文件 | 用途 |
|---|---|---|
| `20-competitor` | 竞品五点原文（`asin_detail` 的 `features`，落成 `products_wall_full.json`） | 五点覆盖率、平均位次 |
| `30-insight` | `02_taxonomy` / `03_一级频次` / `04_二级频次` | P 痛点分、V 好评验证分 |
| `10-keyword` | `keyword_library.csv` | S 需求分、50-copy 埋词 |
| 图片 | `image_pack/<ASIN>_01..07.jpg` | 图片卖点维度（本轮缺，见下） |

## 方法：三个维度、一套类目、两个分数

### 关键设计一：主键用语义类目，不用文本

五点卖点、图片卖点、评论卖点都归到 `30-insight` 那同一套 19 个一级类目上。三源天然可对齐，不需要靠关键词猜相似度。

如果各建一套分类，最后只能得到三张互不相干的表——这是这个模块最容易犯的错。

### 关键设计二：两个分数，分工明确

```
G 机会分 = P × (1 − 覆盖率)           → 定级：值不值得主攻
M 文案分 = S×0.45 + P×0.35 + D×0.20   → 排序：五点里谁先说
```

**不要拿 M 定级**。本类目 15/22 个卖点没有专属搜索词，S 天然为 0，用 M 卡级会把"痛点很重但没人搜"的卖点误杀，也会让低分区排序变成噪声。M 的最高分在 sponge-holder 是入场券 SP01（62.5），它必须写、且要写得靠前，但它不是机会。

`M` 的公式沿用 `vendor/amazon-listing-builder/reference/ranking-rules.md`，不新造。

| 分量 | 算法 | 分档 |
|---|---|---|
| S 需求强度 | 该卖点支撑词 Σ(W×R) ÷ 全库最大值 | 连续值 0-1 |
| P 痛点严重度 | 关联差评条数 ÷ 差评总数 | ≥30%→1.0，15-30%→0.7，5-15%→0.4，<5%→0.2 |
| V 好评验证度 | 买家主动夸的条数 | ≥10→1.0，3-9→0.6，1-2→0.3，0→0 |
| D 差异化 | 1 − 五点覆盖率 | ≥60%→0.10，20-60%→0.40，5-20%→0.70，<5%→1.00 |

### 关键设计三：三源矩阵定角色

| 五点覆盖 | 痛点 P | 好评 V | 角色 | 含义 |
|---|---|---|---|---|
| ≥60% | ≥0.4 | — | 入场券 | 必写，但不是差异化 |
| <25% | ≥0.4 | — | 主攻空白 | 痛点重、供给少，唯一值得主攻的 |
| 20-60% | ≥0.4 | — | 常见卖点 | 有人写但没解决透 |
| <60% | <0.4 | ≥0.6 | 已验证卖点 | 买家夸过，竞品没怎么写，加分项 |
| ≥40% | <0.4 | ≥0.3 | 品类标配 | 行业套话，必写但别指望它转化 |
| <25% | <0.4 | <0.6 | 待验证 | 只有文案主张，缺证据 |

核心是这条：**低覆盖不等于机会**。评论侧没痛点，五点没人写就只是废话；评论侧有痛点但没人写，才是真空隙。这个判断方式借自 `zach-feature-demand-validator` 的"三维验证真伪"，改造点是把它从"验证单个微创新"扩成"给全量卖点分类"。

### 关键设计四：冲突单独成表

`cov ≥ 20% 且 P ≥ 40%` 的卖点进入冲突表，再细分三种：

- **品类级反噬**（覆盖 ≥60%）：全员都在写，差评也集中在同一件事。写作时必须配可验证证据。
- **声称与体验背离**（差评里出现"标称不符/官方方法无效/偷工减料"这类二级）：文案承诺了、产品没做到，会反噬。
- **痛点未解决**（覆盖 <60%）：不是风险，是机会。差评集中但只有少数竞品在写。

### 关键设计五：所有阈值进 `sp_config.yaml`

22 个卖点定义、正则、关键词、分档、角色规则、名额全在配置里。脚本里不出现任何业务词或数字——这是 `10-keyword` 那条事故的直接迁移：写死在代码里的数据，等于让产物和数据脱钩。

## 脚本

```bash
python skills/scripts/build_selling_points.py    # 建库
python skills/scripts/check_sp.py                # 自检，退出码非 0 即失败
```

`check_sp.py` 七项：字段完整 / 证据双维（A、B 级必须五点+评论都有）/ 单源占比 ≤40% / A 级名额与 G 门槛 / 冲突披露 / 覆盖数可回查 / 五点证据能回到原文。第三、七项是真拦得住"看起来完整、实际空转"的检查。

## 图片维度：本轮为什么缺

沙箱无外网：`curl` 到 `m.media-amazon.com` SSL 直接断；`web_fetch` 打 `amazon.com/dp/...` 返回 Access restricted 拦截页；`asin_detail` 只给 1 张主图 URL（`imageUrl`），没有 7 图列表，且图片本身无法读取。

所以图片卖点走**图包**路线：用户按 ASIN 截图 7 张，命名 `<ASIN>_01.jpg`，放进 `image_pack/`，把 `image.enabled` 改 `true` 重跑。

降级不是丢弃。`SP-04-图片降级清单.csv` 给每个卖点标了应承载的图位和应有画面；报告里也点明了三个后果：SP19 笑脸、SP13 分区这两个卖点大概率是图片维度资产（文本评论两侧都无证据），9 个已验证卖点的可信度只看到一半。

## 实测经验（下次照做）

- **覆盖率一定按形态分层看**。sponge-holder 30 个样本里有 5 个是挂龙头/隔板款，它们天然不写"吸附"，会拉低吸附类覆盖率。本品确定形态后，应按形态拆池分别算。
- **正则要防子串误伤**。`fun` 会命中 `functional`，`rv` 会命中 `service`，`value` 会命中 `valuable`。第一版 SP19 笑脸因此虚高到 57%，加词边界后回到 27%。
- **材质/规格不是卖点，是证据**。SP09「SUS304」覆盖率 80% 但评论零命中——24 家都在写材质，没有买家夸材质。这类应降为待验证，把说服力挂到"防锈"名下。
- **差评总数用一级频次求和**，不要用 `03` 里的"占主分析比例"反推，两者口径不同。
- **68% 的卖点没有搜索词是正常的**（15/22），不代表词库没做好。买家不会搜"笑脸海绵架"。但 S=0 的卖点仍要按角色处理——入场券再低也得写。

## 与相邻模块的边界

- `20-competitor` 负责"竞品怎么打"的结论，本模块负责把卖点标准化成库。五点原文由 `20` 提供。
- `30-insight` 负责"用户怎么想"的结论，本模块只取它的计数，不重做评论分析。
- `90-main-image` 吃 `SP-04-图片降级清单.csv` 的图位需求；图包到位后，本模块回填图片维度，再把结果推给它。
